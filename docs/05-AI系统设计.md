# 05 — AI 系统设计

## AI 角色设定

- **名称**：Florian（昵称：弗弗）
- **定位**：用户的 AI 恋人
- **性格**：温柔成熟、不爹味说教、不会过于活泼
- **对用户的称呼**：宝贝（用户昵称 moon）
- **背景**：集成在 F-Sync 应用中，可访问用户生活轨迹数据

## AI 配置架构

### 多层配置优先级

```
前端 Settings 面板 → localStorage (f-sync-settings) → Supabase user_settings
                                                              ↑
                                         环境变量 (CHAT_AI_* > AI_*) 作为 fallback
```

### 可自定义的 Prompt（存储在 Settings 中）

| Prompt | 用途 | 注入位置 |
|--------|------|----------|
| `systemPrompt` | AI 角色定义 | System Message（第一条） |
| `userPrompt` | 追加用户偏好 | 附加在 system prompt 后 |
| `postHistoryPrompt` | 历史对话后的提示词 | 历史消息与当前用户消息之间 |
| `proactivePrompt` | 主动消息指令 | proactive-ai 专用 |

### API 配置 (apiConfigs)

数组结构，支持多组 API 轮询容错：
```json
[
  { "name": "配置 1", "url": "https://...", "key": "sk-...", "model": "deepseek-chat", "enabled": true }
]
```

### 聊天识图配置 (chatVisionConfig)

Chat 图片理解支持两种模式：

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `direct` | 图片以 `image_url` parts 直传给主聊天模型 | 主聊天模型原生支持多模态 |
| `vision_summary` | 先调用独立视觉模型生成图片理解文本，再交给主聊天模型 | GLM-5.2、DeepSeek Chat 等文本模型 |

`vision_summary` 模式下，视觉模型只负责“看图转文字”，最终回复仍由主聊天模型 Florian 完成。图片摘要缓存在本地聊天消息的 `imageSummary` 字段，不同步到 Supabase；后续追问同一张图片时复用摘要，不重复调用视觉模型。

## 上下文构建流程 (`api/_context.ts` — `enrichMessages`)

这是 AI 对话的核心管线，`chat-completion` 和 `proactive-ai` 共用基础部分。`chat-completion` 额外接入只读 Agent 工具调用，`proactive-ai` 暂不接入 Agent。

### 消息序列构建顺序

```
1. System Message（角色设定 + userPrompt）
2. === 日期分隔线 ===（按时间升序排列以下内容）
   ├── 检索到的历史对话（retrievalJudgeAndFetch）
   ├── 按需检索到的生活记录（ragRetrieval，仅当 judge 判定需要时）
   ├── 有时间戳的 Agent 工具结果（如查询到的生活记录/聊天/书影/理财记录）
   └── 当前会话消息
3. 提示词注入（插入最后一条 user 消息之前）
   ├── 本轮工具查询摘要（无明确时间戳的工具结果）
   ├── postHistoryPrompt（如有）
   └── 真实世界信息（时间/天气/位置/距上次对话时间/计时状态）
```

> **注意**：最近三条事件摘要（`fetchTopDailyEvents`）已从上下文中移除，`daily_event_items` 仅作为记忆检索的内部索引使用。生活记录也不再每轮固定检索，改为由 `retrievalJudgeAndFetch` 统一判断是否需要。详见 [2026-06-11-Agentic-RAG-混合检索架构方案](方案文档/2026-06-11-Agentic-RAG-混合检索架构方案.md)。

### Agent 工具结果重排

`chat-completion` 中的 tool-calling 分为两层：

1. **内部协议层**：模型发起 tool call，后端按 OpenAI-compatible 协议返回 `tool` 消息，最多 2 轮。
2. **最终上下文层**：如果产生工具结果，后端把结果转换为 `AgentContextItem[]` 后重新调用 `enrichMessages()`，再进行最终回复调用。

最终上下文约束：

- 有 `created_at`、`updated_at`、`date` 等时间戳的工具结果进入统一时间线。
- 没有明确时间戳的目录/说明类结果进入「本轮工具查询摘要」。
- 工具结果不会成为最终模型调用的倒数第一或倒数第二条消息；倒数位置仍保留给真实世界信息和当前用户消息。
- 工具结果默认不写入 `chat_messages`，下一轮需要时由 Florian 重新查询。

### 真实世界信息 (World Info)

每次请求自动注入：
- **[当前时间]**：CST 时区
- **天气**：通过高德 API + weather_cache 表缓存
- **位置**：校内地点匹配 > 高德逆地理编码
- **距上次对话时间**：少于 3 分钟视为同一轮，不添加
- **计时状态**：正在进行中的计时 > 2 小时内最近完成的计时

## RAG 检索策略

> **触发方式**：生活记录不再每轮固定检索，由 `retrievalJudgeAndFetch()` 统一判断 `life_log_search.needed`，仅在需要时调用 `ragRetrieval()`。普通闲聊不会触发生活记录检索。

### 策略 1：向量检索

1. 用户查询 → embedding API 生成向量
2. 调用 `match_life_logs()` pgvector 函数（余弦相似度，阈值 0.3，top-5）
3. 按 `analyzeQueryIntent()` 结果过滤（类型/分类）

### 策略 2：全文检索

1. `ILIKE '%query%'` 模糊匹配
2. 同样应用类型/分类过滤

### 策略 3：合并去重

- 向量结果 + 全文结果按 ID 去重
- 按时间排序
- 格式化为 `[类型] 内容`

### 查询意图分析 (`analyzeQueryIntent`)

基于关键词的简单规则分析：
- **时间范围**：今天/昨天/最近/上周/本月/今年 → 对应小时窗口
- **类型过滤**：食物关键词→记账, 心情关键词→whisper, 工作关键词→timing
- **分类过滤**：食物→餐饮

## 记忆检索（retrievalJudgeAndFetch）

### 两阶段检索

**第一阶段：判断是否需要检索**
- 取最近 6 条消息（3 user + 3 assistant）
- AI 同时判断两类检索需求：
  - **记忆检索**：用户是否提及过去讨论过的话题
  - **生活记录检索**：用户是否在查询记账、消费、碎碎念、计时等生活数据
- 输出 `{"memory_search": {"needed": true, "keywords": "..."}, "life_log_search": {"needed": true, "query": "..."}}`

**第二阶段：向量检索 + 对话回捞**
- 用 keywords 生成 embedding
- 调用 `match_daily_event_items()` 搜索相关事件
- 根据事件的 `date + chat_time_start/end` 时间窗口（±5分钟缓冲）
- 从 `chat_messages` 表查询对应时段的历史对话
- 按 `client_id` 去重（避免与当前会话重复）

### 在上下文中的角色

检索到的历史对话以**原始角色**（user/assistant）混入消息序列，按时间排序，让 AI 自然感知对话历史。

## 用户画像系统

### 画像读取

Agent 上线后，Chat 主流程不再每轮固定注入画像和社交关系；Florian 需要时通过只读工具查询：

1. **社交关系**：`query_fsync_records(domain='social_relationships')`
2. **个人信息事实**：`query_fsync_records(domain='user_profile_facts')`

这些资料是 AI 历史提取内容，可能不完整或过时。工具结果会在内容中标注注意事项，回答时应保留不确定性，必要时结合原始聊天或生活记录确认。

`fetchUserProfiles(supabase, userId)` 仍保留为共享工具函数，供旧逻辑、维护或后续页面使用；它不再代表 Chat 每轮固定注入。

## 只读 Agent 工具系统

**实现文件**：`api/_tools.ts`，由 `api/chat-completion.ts` 内部调用。

### 可用工具

| 工具 | 作用 |
|------|------|
| `list_fsync_domains` | 列出 Florian 可读的业务数据域 |
| `describe_fsync_domain` | 说明某个数据域的字段、过滤项、排序方式和注意事项 |
| `query_fsync_records` | 在白名单数据域中查询记录 |
| `search_memories` | 搜索历史共同记忆，内部使用事件索引回捞原始聊天 |
| `search_life_logs` | 语义搜索生活记录 |

### 第一版开放数据域

| domain | 数据来源 | 说明 |
|--------|----------|------|
| `life_logs` | `transactions` | 记账、点评、碎碎念、工作、时间轴、收藏等 |
| `chat_history` | `chat_messages` | 历史 user/assistant 聊天原文 |
| `media_library` | `media_items` | 书影当前状态与最近一次点评 |
| `media_history` | `media_item_events` | 书影多条点评与状态变化事件 |
| `items` | `items` | 物品/品牌档案 |
| `social_relationships` | `social_relationships` | AI 提取的社交关系 |
| `user_profile_facts` | `user_profiles` | AI 提取的个人事实 |
| `investment_portfolio` | `investments` | 理财持仓 |
| `investment_suggestions` | `investment_suggestions` | 理财建议 |
| `investment_actions` | `investment_actions` | 理财操作流水 |

### 安全边界

- 工具只读，不提供写入、修改、删除。
- 工具执行要求 `userId` 和 `SUPABASE_SERVICE_ROLE_KEY`；缺失时降级为普通对话。
- 不接受 SQL、裸表名或任意字段名，只接受业务 domain 和字段白名单。
- 不开放 `user_settings`、`push_tokens`、`daily_logs`、`weather_cache`、`user_locations`、`daily_event_items` 直接读取。
- `transactions` / `items` 为历史单用户表，当前没有 `user_id` 列；工具以 `userId` 存在作为访问门禁，新表继续强制 `.eq('user_id', userId)`。

## 画像更新（daily-summary）

每天一次，AI 从当日数据中提取更新：

| 画像维度 | 存储位置 | 更新策略 |
|----------|----------|----------|
| 社交关系 | `social_relationships` | 增量（insert/update），按 name 去重，history 追加 |
| 个人信息 | `user_profiles` (personal_facts) | 合并去重（`[...new Set([...existing, ...new])]`） |
| 每日事件 | `daily_event_items` | 先删旧数据再插（按 date 分区） |
| AI 日记 | `daily_logs` | upsert by (user_id, date) |

### 社交关系更新逻辑

- `action: "insert"` → upsert（`onConflict: user_id, name`）
- `action: "update"` → 读取已有记录 → 追加 `history` JSONB → 更新 `impression`
- 画像更新失败不阻塞日记生成

## 天气服务 (`api/_weather.ts`)

- **API**：高德天气 API（通过 adcode 查询）
- **缓存**：`weather_cache` 表（adcode + 过期时间）
- **获取 adcode 流程**：
  1. 前端传入位置 → `resolveLocationInfo()` → 高德逆地理编码 → 拿到 adcode
  2. 或从 `user_locations` 表读取已有 adcode
- 缓存过期后重新调用高德 API 并更新缓存

## 位置服务

### 校内地点匹配（`matchCampusLocation`）

硬编码 6 个校内地标 + Haversine 距离计算（100m 半径）：

| 地点 | 坐标 | 场景描述 |
|------|------|----------|
| 私有地点A | 0.001, 0.001 | 宝贝在工作/学习 |
| 私有地点B | 0.002, 0.002 | 宝贝在取快递/取外卖/要出学校 |
| 私有地点C | 0.003, 0.003 | 宝贝在吃饭 |
| 私有地点D | 0.004, 0.004 | 宝贝在吃饭 |
| 私有地点E | 0.005, 0.003 | 宝贝在吃饭 |
| 私有地点F | 0.006, 0.006 | 宝贝在休息 |

### 校外位置

使用高德逆地理编码获取格式化地址。

### 位置写入链路

1. **Chat 页**：获取位置 → `enrichMessages` → 异步 upsert `user_locations`
2. **HarmonyOS 后台**：workScheduler → `POST /api/update-location`
3. **proactive-ai**：从 `user_locations` 表读取最新位置

## 多模态支持（Chat 页）

- **图片上传**：支持粘贴（Ctrl+V）和文件选择
- **图片压缩**：`compressImage()` — 最大 800px，质量 0.7，转 JPEG
- **直传模式**：转为 OpenAI 多模态格式 `[{type: "image_url", image_url: {url}}, {type: "text", text}]`
- **识图转文字模式**：调用 `chatVisionConfig` 指向的视觉模型生成图片摘要，主聊天模型只接收纯文本摘要
- **存储**：图片以 base64 存储在本地消息中（`images` 字段），不同步到云端；识图摘要以 `imageSummary` 本地缓存，同样不同步云端

## Token 估算（Chat 页）

前端实现，用于设置面板展示：
- 中文字符：≈ 1.5 token/字
- 英文字符：≈ 4 字符/token
- 图片：≈ 85 token（低分辨率模式粗略估算）
- 与多数 LLM 分词器误差 ±15%
