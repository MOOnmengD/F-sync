# 聊天独立识图模型配置

> 状态：已实现（真实视觉模型联调待部署后验证）
> 日期：2026-07-07
> 说明：本方案只设计 Chat 图片理解的独立视觉模型链路，不替换主聊天模型，不新增公开 Serverless Function。

---

## 功能名称

为 AI 聊天增加可选的独立识图模型配置，使 GLM-5.2 等文本输入/文本输出模型也能理解用户发送的图片。

---

## 背景与动机

当前 Chat 页已支持用户粘贴或选择图片，后端会把图片转成 OpenAI 多模态格式：

```text
[{ type: "image_url", image_url: { url } }, { type: "text", text }]
```

这适合原生多模态聊天模型，但不适合 GLM-5.2 这类文本模型。以智谱为例：

- GLM-5.2 是文本输入、文本输出模型，但具备长上下文、Function Call、MCP 等 Agent 能力。
- GLM-4.6V 是视觉理解模型，可以接收 `image_url` 与文本，输出文字理解结果。

因此更合适的架构不是用视觉模型取代聊天模型，而是在 F-Sync 后端加一个“视觉预处理”步骤：

```text
用户图片 + 用户文字
  → 独立视觉模型生成图片说明/OCR结果
  → 主聊天模型接收文字版图片上下文
  → Florian 保持原有聊天模型、人设、RAG、Agent 工具与最终回复职责
```

F-Sync 已有类似先例：理财截图 OCR 使用单独视觉模型识别截图，再把结构化结果交给理财功能处理。本方案将同类思想迁移到 Chat 图片理解，但用途更通用。

---

## 设计目标

- [x] 保留现有“图片直传主聊天模型”的能力，避免破坏原生多模态模型体验。
- [x] 新增“独立识图转文字”模式，让文本聊天模型也能回答图片相关问题。
- [x] 识图模型配置独立于主聊天模型；主模型仍负责最终回复和 Florian 人设。
- [x] 不新增公开 API 文件，避免触碰 Vercel Hobby 12 个 Function 限制。
- [x] 不修改数据库结构，优先复用 `user_settings.settings` JSON 与本地 chat store。
- [x] 识图结果带有不确定性提示，降低视觉模型误读造成的幻觉。

---

## 非目标

- 第一版不做“主模型主动调用 analyze_image 工具”的复杂工具链。
- 第一版不自动判断某个模型是否原生支持多模态，由用户在设置中选择图片处理模式。
- 第一版不把图片 base64 上传到 Supabase。
- 第一版不把识图摘要写入数据库长期记忆；如后续需要让日记/记忆系统理解图片，再单独设计。
- 第一版不处理视频、PDF、文件理解，只处理 Chat 中的图片。

## 设计方案

### 图片处理模式

在 Chat 设置中新增“图片理解”配置，第一版提供两种模式：

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `direct` | 沿用当前逻辑，把图片作为 `image_url` 直接发给主聊天模型 | 主聊天模型本身支持多模态 |
| `vision_summary` | 先调用独立识图模型，把图片转成文字，再把文字交给主聊天模型 | 主聊天模型是 GLM-5.2、DeepSeek Chat 等文本模型 |

默认值为 `direct`，保证升级后现有行为不变。

### 设置结构

在 `AISettings` 中新增：

```typescript
type ChatImageMode = 'direct' | 'vision_summary'

interface ChatVisionConfig {
  mode: ChatImageMode
  url: string
  key: string
  model: string
  prompt: string
}
```

字段含义：

| 字段 | 说明 |
|------|------|
| `mode` | 图片处理模式；默认 `direct` |
| `url` | 独立识图 API URL；空值时可复用当前启用的主聊天配置 URL |
| `key` | 独立识图 API Key；空值时可复用当前启用的主聊天配置 Key |
| `model` | 视觉模型名，例如 `glm-4.6v`；不 fallback 到主聊天模型名，避免把图片发给文本模型 |
| `prompt` | 自定义识图提示词；空值使用内置通用提示词 |

### 配置优先级

后端解析视觉模型配置时使用以下优先级：

```text
url:
  settings.chatVisionConfig.url
  → CHAT_VISION_AI_API_URL
  → 当前第一组启用的主聊天 API 配置 url

key:
  settings.chatVisionConfig.key
  → CHAT_VISION_AI_API_KEY
  → 当前第一组启用的主聊天 API 配置 key

model:
  settings.chatVisionConfig.model
  → CHAT_VISION_AI_MODEL
```

注意：`model` 不使用 `CHAT_AI_MODEL` / `AI_MODEL` fallback，因为这些通常是文本模型。若 `vision_summary` 模式下缺少视觉模型名，API 应返回明确错误，提示用户配置聊天识图模型。

### 默认识图 Prompt

建议内置默认提示词：

```text
你是 F-Sync 聊天中的图片理解助手。请仔细理解用户上传的图片，并输出一段给主聊天模型使用的中文图片上下文。

请按图片顺序描述：
1. 画面中明确可见的主体、场景、物品、人物动作或界面内容。
2. 图片中可读文字，尽量原样摘录；看不清的部分标注“看不清”。
3. 与用户文字问题直接相关的信息。
4. 不确定之处，不要编造图片中看不见的细节。

输出要求：
- 使用简洁中文。
- 不要替用户做最终聊天回复。
- 不要延续 Florian 人设，不要称呼用户。
- 不要输出 Markdown 表格。
- 如果图片无法判断，请明确说明无法判断的原因。
```

### 数据流

`direct` 模式沿用现有流程：

```text
Chat.tsx 发送文本 + images
  → /api/chat-completion
  → enrichMessages()
  → convertMessagesForApi(): images 转为 image_url parts
  → 主聊天模型直接看图并回复
```

`vision_summary` 模式新增预处理：

```text
Chat.tsx 发送文本 + images + chatVisionConfig
  → /api/chat-completion
  → 若图片消息已有 imageSummary：复用缓存
  → 若没有 imageSummary：调用视觉模型生成图片摘要
  → 把当前用户消息改写为纯文本：
      用户原文

      [图片理解结果]
      图片1：...
      图片2：...
      以上结果由独立视觉模型生成，可能存在误读。
  → enrichMessages()
  → Agent 工具循环和最终回复继续使用主聊天模型
  → API 返回 AI 回复，同时返回本轮新生成的 imageSummary
  → Chat.tsx 把 imageSummary 写回本地消息缓存
```

### 与 Agent 工具的关系

第一版把识图放在 Agent 工具循环之前，作为输入预处理，而不是让主模型通过 tool calling 主动调用。

原因：

- 不同 OpenAI-compatible 服务的 tool calling 兼容性不稳定。
- 文本模型无法直接消费图片，必须先有一段文字上下文。
- 预处理模式延迟和失败路径更可控。
- 现有 F-Sync Agent 工具是只读数据查询；视觉理解属于另一类外部感知能力，后续可单独扩展为工具。

后续可选增强：

```text
用户追问“再仔细看左下角”
  → 主模型调用 analyze_image 工具
  → 后端用原图 + 追问局部提示重新调用视觉模型
  → 工具结果进入最终上下文
```

此增强不属于第一版。

### 本地图片摘要缓存

在 `ChatMessage` 中增加可选字段：

```typescript
interface ChatMessage {
  id: string
  role: 'user' | 'assistant' | 'system'
  content: string
  thinking?: string
  createdAt: number
  isSynced?: boolean
  images?: string[]
  imageSummary?: string
  imageSummaryModel?: string
}
```

用途：

- `imageSummary` 本地持久化到 `localStorage`，避免用户追问同一张图片时重复调用视觉模型。
- `imageSummary` 不同步到 Supabase，延续当前图片“本地消息中保存、不同步云端”的隐私边界。
- 如果刷新后本地缓存仍在，下一轮可直接使用摘要；如果用户清空本地聊天或换设备，则图片和摘要都会消失。

前端发送上下文时：

- `direct` 模式：继续只给最后一条带图片的用户消息附带 `images`。
- `vision_summary` 模式：
  - 若该消息已有 `imageSummary`，发送 `imageSummary`，不再发送 `images`。
  - 若没有 `imageSummary`，发送 `images` 给后端生成摘要。

### API 返回扩展

`/api/chat-completion` 在原始 AI 响应基础上可附加：

```typescript
interface ChatVisionResult {
  messageCreatedAt: number
  model: string
  summary: string
}

{
  choices: [...],
  fullMessages: [...],
  imageUnderstanding?: ChatVisionResult[]
}
```

`messageCreatedAt` 用于前端定位本地用户消息并写回缓存。若实现时发送 `id` 更方便，也可以改用 `messageId`。

### 视觉模型调用格式

使用 OpenAI-compatible Chat Completions：

```json
{
  "model": "glm-4.6v",
  "messages": [
    {
      "role": "user",
      "content": [
        { "type": "text", "text": "默认或自定义识图 Prompt + 用户原文" },
        { "type": "image_url", "image_url": { "url": "data:image/webp;base64,..." } }
      ]
    }
  ],
  "temperature": 0.1,
  "max_tokens": 2048
}
```

多图时可在同一条消息中按顺序附加多个 `image_url`。若真实测试发现某个提供方多图不稳定，再退化为逐张调用并合并摘要。

### 上下文展示

ContextViewerModal 中展示的是最终发给主聊天模型的 `fullMessages`：

- `direct` 模式：仍可看到 `image_url` parts。
- `vision_summary` 模式：看到纯文本图片理解结果，方便确认主聊天模型实际读到了什么。

## 边缘情况

- [ ] `vision_summary` 模式但缺少视觉模型名：返回明确错误，提示配置聊天识图模型。
- [ ] `vision_summary` 模式但缺少 URL/Key：若无法从当前主聊天配置或环境变量补齐，返回明确错误。
- [ ] 视觉模型不支持 `data:image/...` 或 `image_url`：返回上游错误摘要，前端显示失败信息。
- [ ] 视觉模型返回空内容：返回“图片理解结果为空”的错误，不让主聊天模型凭空猜图。
- [ ] 视觉模型摘要过长：后端截断到安全长度，例如 3000 字符，并标注已截断。
- [ ] 多图上传：按顺序生成图片1、图片2等摘要。
- [ ] 纯图片无文字：用户原文为空时仍能生成 `[图片理解结果]`。
- [ ] 用户追问同一张图：优先复用本地 `imageSummary`，避免重复识图。
- [ ] 用户切换视觉模型后追问旧图：如果 `imageSummaryModel` 与当前模型不同，第一版仍复用旧摘要；后续可增加“重新识图”按钮。
- [ ] `direct` 模式主模型不支持多模态：保持现有行为，由上游返回错误；用户可切换到 `vision_summary`。
- [ ] Agent 工具调用失败：与现有降级逻辑一致，不影响已经生成的图片摘要。

---

## 与现有功能的交互

- **Chat 多模态直传**：默认保持不变。
- **只读 Agent 工具**：识图摘要在工具调用前进入用户消息文本，Agent 可基于摘要决定是否查询 F-Sync 数据。
- **RAG / 记忆检索**：`vision_summary` 模式下，当前用户消息包含图片摘要，检索判断可参考图片文字；但第一版不把摘要写入长期记忆。
- **TTS**：不受影响，只朗读最终 AI 回复。
- **理财截图 OCR**：不替代 `investment(type=ocr)`；理财功能仍用专门提示词和结构化 JSON。
- **设置同步**：新增 `chatVisionConfig` 存入 `user_settings.settings`，无需数据库迁移。
- **每日摘要**：第一版不会读取图片摘要，因为摘要不写入 `chat_messages`。

---

## 安全与隐私

- `vision_summary` 模式下，图片会发送给独立视觉模型提供方；主聊天模型只收到文字摘要。
- `direct` 模式下，图片仍直接发送给主聊天模型提供方。
- 图片与识图摘要默认只保存在本地 `localStorage`，不上传 Supabase。
- API Key 只用于后端请求，不返回给前端上下文查看器或调试信息。
- 识图 Prompt 必须要求模型标注不确定内容，不允许编造看不见的细节。
