## 一、功能名称

F-Sync AI 对话的混合式记忆检索与 Agent 工具调用架构。

---

## 二、背景与动机

### 2.1 目标场景

用户曾在过去的对话中描述一件事情，例如通宵后凌晨回宿舍时遇到一只叫声特别、只能看到圆肚子的小鸟。半个月后，用户确认这只鸟是极北柳莺，并希望 Florian 能回忆起当时的对话。

F-Sync 当前已经具备以下记忆链路：

```text
当前对话
  -> AI 判断是否需要检索
  -> 生成一个检索短语
  -> 向量匹配 daily_event_items
  -> 根据事件日期和 chat_time_start/chat_time_end
     回捞 chat_messages 原文
  -> 将历史原文按真实时间加入统一时间线
```

这套设计的核心方向是合理的：

- `daily_event_items` 是经过压缩的记忆索引，适合在大量历史对话中定位事件；
- `chat_messages` 是共同经历的原始内容，最终应尽量回捞原文，而不是只把事件摘要交给 Florian；
- 所有内容按真实发生时间排序，有利于保持生活与对话的时间连续性。

### 2.2 当前主要问题

#### 问题 A：是否检索完全依赖一次模型判断

当前 `retrievalJudgeAndFetch()` 让模型判断 `needs_retrieval`。如果模型没有识别到隐含的回忆指代，后续检索链不会启动。

#### 问题 B：只生成一个检索短语

用户当前知道的名称和过去描述事情时使用的语言可能完全不同：

```text
现在：极北柳莺
当时：小鸟、叫声特别、凌晨、通宵后、回宿舍、圆肚子
```

如果只使用“极北柳莺”生成 embedding，事件摘要中又没有这个后来才知道的名称，向量检索可能无法命中。

#### 问题 C：事件索引失效后没有直接搜索聊天原文的回退路径

事件可能没有被每日摘要提取，也可能因摘要措辞不同而检索失败。当前事件层没有命中时，系统无法直接通过关键词和日期范围搜索 `chat_messages`。

#### 问题 D：生活记录每轮都会检索

当前 `chat-completion.ts` 每轮都构造 `searchQuery` 并调用 `ragRetrieval()`。普通闲聊也会注入不相关的记账、碎碎念或计时记录，增加噪音和上下文长度。

#### 问题 E：最近三条事件摘要固定进入最终上下文

`fetchTopDailyEvents()` 返回的事件摘要既是索引数据，又直接出现在 Florian 的上下文中。它们不一定与当前话题有关，也可能使已经结束的历史事件被模型错误延续到当前现实。

### 2.3 本方案的基本判断

本方案不把问题简化为“要求模型在找不到时承认不知道”。首要目标是提高真正找回共同记忆的概率，同时控制延迟和无关信息。

检索架构采用两类能力互补：

1. **程序编排的基础检索**：保证不同模型下稳定触发、稳定回退；
2. **Tool-calling 主动检索**：让 Florian 在初始结果不足或需要进一步了解时主动补查，逐步获得接近 AI Agent 的数据访问能力。

## 三、设计目标

- [ ] 明确回忆场景不因模型漏判而完全跳过检索。
- [ ] 一次规划生成 1-5 组检索短语，覆盖当前名称、旧称、场景和特征。
- [ ] 保留“事件摘要定位 -> 历史聊天原文回捞”的主路径。
- [ ] 事件索引未命中时，通过关键词和日期范围直接搜索历史聊天。
- [ ] 历史对话与生活记录分别判断是否需要检索，普通闲聊不再强制检索生活记录。
- [ ] 保留全量上下文的统一时间顺序，不改为按来源分模块。
- [ ] 移除最近三条事件摘要的固定注入，但继续保留事件表作为内部索引。
- [ ] 保留现有原始对话定位方式和最后一条 `<thinking>` 的上下文设计。
- [ ] 在真实应用编码前，用现有历史样本建立独立检索测试集。
- [ ] 为后续 Tool-calling 和更多 Supabase 数据工具保留扩展路径。

## 五、总体架构

### 5.1 完整数据流

```text
用户发送消息
  |
  v
检索硬触发规则（代码）
  |  判断明确的历史回忆 / 生活数据意图
  v
检索规划器（一次轻量 AI 调用）
  |  输出是否检索历史、是否检索生活记录、1-5 组检索短语
  v
时间表达解析器（代码，以当前 CST 时间计算）
  |  将“15天前 / 上个月底 / 5月28日”转换为日期范围
  |
  +--------------------------+
  |                          |
  v                          v
历史记忆检索                 生活记录检索
  |                          |
  | 事件向量 + 事件关键词     | 按需执行现有 RAG
  |      |                   | 可使用类型和日期过滤
  |      v                   |
  | 回捞历史聊天原文          |
  |      |                   |
  | 未命中则搜索 chat_messages|
  |      |                   |
  | 复用 +/- 5 分钟回捞       |
  +-------------+------------+
                |
                v
历史原文、生活记录、当前对话、真实世界信息
按实际时间统一排序
                |
                v
Florian 生成回复（后续阶段可继续调用工具补查）
```

### 5.2 为什么采用“代码 + 模型”的混合判断

只使用代码规则无法理解所有自然语言，只使用模型判断又会受模型能力、性格和 API 提供方差异影响。

因此采用以下优先级：

```text
明确硬触发命中 -> 强制开启对应检索
没有命中硬触发 -> 使用检索规划器的语义判断
两者任一认为需要检索 -> 执行检索
```

代码规则只负责高确定性场景，不试图替代完整语义理解。

## 六、检索触发与规划

### 6.1 代码层硬触发

#### 历史记忆检索硬触发

以下表达出现时，强制 `memory_search = true`：

- 明确记忆询问：`还记得`、`记不记得`、`你记得吗`；
- 明确共同对话指代：`之前跟你说过`、`我以前说过`、`上次聊到`；
- 明确过去对象指代：`那次`、`那天`、`当时`、`上次那个`；
- 与过去时间表达共同出现的事件描述：`几天前`、`半个月前`、`上个月`、具体日期等。

硬触发规则不负责生成最终查询，只保证检索不会因模型漏判而跳过。

#### 生活记录检索硬触发

以下场景强制 `life_log_search = true`：

- 消费查询：花了多少、买过什么、最近吃了什么；
- 计时查询：工作多久、睡了多久、今天做了多长时间；
- 明确查询碎碎念、收藏或其他结构化记录；
- 用户明确要求读取、统计或比较 F-Sync 中的生活数据。

普通分享、情绪表达和闲聊不应仅因包含“吃、工作、买”等词就强制检索。

### 6.2 检索规划器

现有检索判断调用升级为一次结构化规划调用，同时判断两类检索并生成查询。

建议输出：

```json
{
  "memory_search": {
    "needed": true,
    "queries": [
      "小鸟 叫声",
      "通宵 凌晨 回宿舍",
      "圆肚子 小鸟",
      "极北柳莺"
    ]
  },
  "life_log_search": {
    "needed": false,
    "query": "",
    "log_types": []
  }
}
```

#### 查询生成原则

每组查询是简短检索短语，不是彼此独立的单字列表。规划器优先覆盖：

1. **当前名称**：现在才知道的正式名称，如“极北柳莺”；
2. **过去可能使用的称呼**：小鸟、鸟；
3. **场景锚点**：通宵、凌晨、回宿舍；
4. **特征锚点**：叫声特别、圆肚子；
5. **人物或地点锚点**：用户明确提到且有区分度的信息。

查询数量限制为 1-5 组，避免过多 embedding 请求和候选噪音。

#### 与硬触发的合并

```typescript
const memoryNeeded = hardTrigger.memory || plan.memory_search.needed
const lifeLogNeeded = hardTrigger.lifeLog || plan.life_log_search.needed
```

如果规划器调用失败：

- 硬触发已命中的检索仍然执行；
- 从当前用户消息中提取去除时间词后的核心文本作为单个回退查询；
- 不因规划器故障阻断正常回复。

### 6.3 短消息处理

不再使用“当前消息少于 10 字就直接拼接上一条消息”作为统一搜索词。

原因是上一条消息可能是 Florian 的回复，其中可能包含扩写、推断或错误信息。短消息应交给检索规划器结合最近对话理解；规划器失败时，才使用“当前用户消息 + 最近一条用户消息”作为回退，不拼接 assistant 消息。

## 七、时间表达处理

### 7.1 `time_hint` 的正确定位

`time_hint` 不是向量检索或关键词检索的文本内容。

例如用户说“前段时间那只鸟”，系统绝不能搜索：

```text
embedding("前段时间")
ILIKE '%前段时间%'
```

因为过去事件发生时，用户通常不会将其描述为“前段时间”。时间表达只用于生成数据库日期范围或搜索优先级。

### 7.2 代码解析结果

时间解析器直接读取当前用户消息，并基于本轮真实 CST 时间计算：

```typescript
interface ParsedTimeRange {
  kind: 'exact' | 'bounded' | 'soft' | 'none'
  start?: string
  end?: string
  raw?: string
}
```

示例：

| 用户表达 | 处理方式 |
|----------|----------|
| `2026年5月28日` | 精确日期 |
| `5月28日` | 根据当前年份推断，必要时处理跨年 |
| `15天前` | 当前 CST 日期减 15 天，可给小范围容差 |
| `半个月前` | 约 15 天前，使用有限日期窗口 |
| `上周末` | 计算上一自然周的周末 |
| `上个月底` | 计算上一个自然月最后若干天 |
| `最近几天` | 近期有限窗口 |
| `前段时间`、`之前` | `soft`，不做严格过滤；近期优先，未命中扩大到全历史 |
| 未提及时间 | `none`，不限制日期 |

### 7.3 严格过滤与软优先

- `exact` / `bounded`：日期条件直接进入数据库查询；
- `soft`：先在合理的近期范围内搜索，未命中后自动扩大至全历史；
- `none`：直接搜索全历史，依靠相关度和结果数量限制控制噪音。

时间换算必须由代码完成，不能依赖最终回复模型自行计算日期。

## 八、历史记忆检索主路径

### 8.1 第一层：事件摘要混合检索

对规划器生成的每组查询执行：

1. `daily_event_items` 向量检索；
2. `daily_event_items.content` 关键词检索；
3. 应用日期范围；
4. 合并并按事件 ID 去重；
5. 保留排名靠前的少量事件候选。

#### 向量请求优化

- 优先使用 embedding API 的数组输入，一次生成多组 query embedding；
- 如果当前 embedding 提供方不支持数组输入，则限制查询数量并并行请求；
- 事件 RPC 每组查询返回少量候选，最终统一去重，避免上下文膨胀。

#### 事件关键词匹配

查询短语需要拆成有意义的锚点，例如：

```text
"通宵 凌晨 回宿舍"
-> ["通宵", "凌晨", "回宿舍"]
```

关键词查询使用 OR 召回候选，再在代码中按命中锚点数量排序，不能直接执行：

```sql
content ILIKE '%通宵 凌晨 回宿舍%'
```

因为历史摘要不一定以相同顺序连续出现这些词。

### 8.2 日期范围必须进入向量 RPC

当前 `match_daily_event_items()` 先从全部事件取 top-5。若调用后才在代码中过滤日期，目标日期内的相关事件可能根本没有进入 top-5。

因此新增或替换为支持用户和日期参数的 RPC：

```sql
match_daily_event_items_v2(
  query_embedding,
  target_user_id,
  date_start,
  date_end,
  match_threshold,
  match_count
)
```

日期为空时不限制；有精确或有限范围时，在向量排序前完成过滤。

### 8.3 回捞历史对话原文

事件候选命中后，完全复用现有方式：

```text
event.date
+ chat_time_start / chat_time_end
+ 前后各 5 分钟缓冲
-> 查询 chat_messages
-> 返回真实 user / assistant 原文
```

本方案不新增消息 ID 关联字段，也不改变现有对话定位方式。

### 8.4 简化的成功条件

不增加额外 AI 判断，也不建立复杂的“结果充分度”评分。

```text
存在达到阈值的事件候选，并成功回捞至少一条历史对话
-> 主路径成功

没有事件候选，或候选无法回捞任何历史对话
-> 进入 chat_messages 关键词回退
```

相似度阈值和候选数量通过离线测试调整，不在第一版引入复杂动态规则。

## 九、历史聊天关键词回退

### 9.1 触发条件

以下任一情况触发直接聊天搜索：

- 所有事件向量和关键词查询均无候选；
- 事件候选缺少有效日期或对话时间；
- 事件候选存在，但没有回捞到聊天原文；
- 后续 Tool-calling 中 Florian 主动要求换词补查。

### 9.2 搜索方法

1. 从多组检索短语中提取、去重高信息量锚点；
2. 在 `chat_messages.content` 中对锚点执行 OR 关键词匹配；
3. 有明确日期范围时直接添加 `created_at` 条件；
4. 限制初始命中数量；
5. 在代码中按命中锚点数、日期吻合程度和时间接近程度排序；
6. 对排名靠前的命中，复用现有前后 5 分钟窗口回捞完整对话；
7. 按消息 ID 去重并按真实时间排序。

### 9.3 关键词长度与性能

`pg_trgm` 适合包含较长片段的模糊匹配，但极短关键词未必能有效利用三元组索引。实现时应：

- 优先使用“回宿舍”“圆肚子”“极北柳莺”等较有区分度的词；
- 单字“鸟”等词仅作为补充锚点；
- 尽可能结合日期范围；
- 对候选数量设置上限，避免扫描结果直接进入上下文。

## 十、生活记录按需检索

### 10.1 改造原则

`ragRetrieval()` 不再在每轮对话中固定执行，只在以下任一条件成立时调用：

- 代码硬触发认为需要生活记录；
- 检索规划器返回 `life_log_search.needed = true`；
- 后续 Agent 主动调用 `search_life_logs`。

### 10.2 检索输入

生活记录使用独立查询，不复用历史聊天的 `memory queries`：

```json
{
  "needed": true,
  "query": "上周买耳机相关支出",
  "log_types": ["记账"],
  "time_expression": "上周"
}
```

时间表达同样由代码解析为数据库日期范围，而不是作为关键词搜索。

### 10.3 注入方式

检索到的生活记录继续作为用户产生的数据加入统一时间线，并保留其原始记录时间。本文不改变其 `user` 角色设计。

## 十一、上下文构建调整

### 11.1 移除固定最近事件

`fetchTopDailyEvents()` 不再由 `enrichMessages()` 每轮调用，最近三条 `daily_event_items` 不再固定进入最终上下文。

`daily_event_items` 继续承担：

- 历史记忆的内部索引；
- 对话原文定位的桥梁；
- 后续日记、时间线或其他功能的数据来源。

### 11.2 保留统一时间线

最终仍将以下内容放入同一个 `timeBoundItems` 集合并按时间升序排列：

- 检索回来的历史对话原文；
- 按需检索到的生活记录；
- 当前连续对话。

系统提示词位于首条；`postHistoryPrompt` 和真实世界信息仍位于当前用户消息之前。

### 11.3 真实世界信息优先级

本方案不修改真实世界信息格式，但历史检索中的日期条件必须以本轮 `[当前时间]` 对应的 CST 日期为计算基准，不能使用历史消息中的时间作为“现在”。

## 十二、Tool-calling 与 Agent 能力

### 12.1 定位

Tool-calling 是 F-Sync 获得 AI Agent 能力的重要基础，但不承担全部基础召回责任。

```text
程序预检索：确保明确记忆场景在不同模型下都能稳定执行
Tool-calling：允许 Florian 主动补查、换词、查询其他数据
```

即使某个模型的 function calling 表现较弱，程序预检索仍能提供基础记忆；擅长工具调用的模型则可在其上继续探索。

### 12.2 第一批工具

#### `search_memories`

```typescript
interface SearchMemoriesArgs {
  queries: string[]       // 1-5 组检索短语
  time_expression?: string
}
```

工具内部复用第八、九章的完整检索链，最终返回历史对话原文，而不是只返回事件摘要。

#### `search_life_logs`

```typescript
interface SearchLifeLogsArgs {
  query: string
  log_types?: Array<'记账' | 'whisper' | 'timing' | '收藏'>
  time_expression?: string
}
```

### 12.3 Agent 循环限制

- 最多 2 轮补充工具调用，初期避免明显延迟和费用增长；
- 每轮允许调用多个互不依赖的工具，并行执行；
- 工具失败时向模型返回简短错误结果，不中断正常回复；
- API 不支持 tools 时，自动退回“程序预检索 + 普通回复”路径；
- 后续根据实际模型表现决定是否增加轮数。

### 12.4 后续可扩展工具

本方案落地后，可逐步开放：

- 获取指定日期的完整生活时间线；
- 查询日记与每日事件；
- 查询社交关系历史；
- 统计消费、计时和情绪趋势；
- 在用户明确授权的功能中写入或更新数据。

这些扩展不属于第一版实现范围。

## 十三、可选的事件索引增强

### 13.1 `search_terms` 的含义

如果离线测试表明事件摘要本身仍难以通过关键词命中，可在每日事件生成时同时提取检索词：

```json
{
  "content": "宝贝凌晨回宿舍时遇到一只小鸟",
  "search_terms": ["小鸟", "鸟叫", "凌晨", "回宿舍", "通宵"]
}
```

`search_terms` 只在“事件摘要关键词检索”阶段使用：

```text
规划器锚点
-> 匹配 daily_event_items.search_terms
-> 定位事件
-> 按现有时间窗口回捞 chat_messages 原文
```

它不直接进入 Florian 的最终上下文，也不取代事件 `content` 的 embedding。

### 13.2 是否实施

该字段不是 Phase 1 必需项。先测试以下链路：

```text
多查询向量检索 + content 关键词检索 + chat_messages 回退
```

只有测试结果证明事件关键词召回仍明显不足时，才新增 `search_terms`，避免未经验证地扩大数据库和每日摘要复杂度。

## 十四、数据库变更

### 14.1 必需索引

新增迁移文件，建议内容：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX IF NOT EXISTS idx_chat_messages_content_trgm
  ON chat_messages USING gin (content gin_trgm_ops);

CREATE INDEX IF NOT EXISTS idx_daily_event_items_content_trgm
  ON daily_event_items USING gin (content gin_trgm_ops);

-- 当前已有独立 user_id 和 created_at 索引；是否增加复合索引
-- 以实际 EXPLAIN 结果为准。
CREATE INDEX IF NOT EXISTS idx_chat_messages_user_created_at
  ON chat_messages (user_id, created_at DESC);
```

### 14.2 事件向量 RPC

新增 `match_daily_event_items_v2`，核心要求：

- 按 `target_user_id` 过滤；
- 支持可空的 `date_start` / `date_end`；
- 在计算 top-N 前完成用户和日期过滤；
- 返回现有事件定位所需的 `date`、`chat_time_start`、`chat_time_end`；
- 保留旧 RPC，待新链路验证后再决定是否移除。

### 14.3 可选字段

仅在测试证明需要时新增：

```sql
ALTER TABLE daily_event_items
  ADD COLUMN search_terms text[];

CREATE INDEX idx_daily_event_items_search_terms
  ON daily_event_items USING gin (search_terms);
```

## 十六、离线测试与评估

### 16.1 为什么先离线测试

F-Sync 没有现成测试框架，真实聊天请求又会产生 API 费用、延迟和情绪体验风险。实现前应使用现有 Supabase 历史数据建立独立检索测试脚本，不生成最终 Florian 回复，只验证检索链。

### 16.2 测试样本格式

```json
{
  "name": "极北柳莺",
  "current_message": "你还记得前段时间我通宵后回宿舍看到的小鸟吗？是极北柳莺哦",
  "expected_date_range": ["实际历史日期", "实际历史日期"],
  "expected_chat_contains": ["小鸟", "叫声"],
  "expected_memory_search": true,
  "expected_life_log_search": false
}
```

测试集应覆盖：

- 当前名称与过去描述不同；
- 有精确日期；
- 有“15天前”“上个月底”等相对时间；
- 只有“前段时间”等模糊时间；
- 事件摘要存在且可命中；
- 事件摘要存在但只能通过多查询命中；
- 事件摘要缺失，需要聊天关键词回退；
- 普通闲聊，不应检索任何数据；
- 查询消费或计时，只应检索生活记录；
- 同时需要历史对话和生活记录。

### 16.3 记录指标

每条样本记录：

- 硬触发是否正确；
- 规划器是否选择正确检索类型；
- 生成了哪些查询短语；
- 时间表达解析结果；
- 事件向量和关键词候选；
- 是否进入聊天回退；
- 最终是否回捞到目标原文；
- 返回的无关消息数量；
- 各阶段耗时和总耗时。

### 16.4 初始验收指标

- 明确“还记得”类样本的检索触发率为 100%；
- 已知目标事件样本中，目标原文进入结果的召回率达到预设测试集的 90% 以上；
- 普通闲聊的生活记录误触发率显著低于当前固定检索；
- 不因规划器或 embedding 失败阻断正常聊天；
- 检索增加的延迟可被记录并据此优化，不先设脱离实测的绝对数值。

## 十七、边缘情况与降级策略

| 情况 | 处理方式 |
|------|----------|
| 规划器 API 失败 | 使用硬触发结果和当前/最近用户消息构造回退查询 |
| embedding API 失败 | 跳过向量检索，继续事件关键词和聊天关键词检索 |
| 时间表达无法解析 | 不做严格日期过滤 |
| 软时间范围未命中 | 自动扩大到全历史 |
| 事件命中但无时间字段 | 进入聊天关键词回退 |
| 聊天关键词过短或过泛 | 优先使用其他锚点、日期范围和 LIMIT 控制 |
| 所有检索均无结果 | 不注入伪造记忆，继续基于当前对话回复 |
| 模型不支持 tools | 使用程序预检索结果进行普通 Chat Completions |
| 工具调用超过上限 | 停止补查，使用已有上下文生成回复 |
| 多个事件同时命中 | 限制候选，回捞后按消息 ID 去重并按时间排序 |

## 十八、实现步骤

### Phase 0：检索测试基线

1. 从真实历史对话中整理一组已知答案样本，包括极北柳莺场景；
2. 编写独立检索调试脚本或 API 调试模式；
3. 记录当前单查询事件向量检索的命中结果和耗时；
4. 固化基线，后续每个阶段重复运行。

### Phase 1：触发与按需检索

1. 增加历史记忆和生活记录硬触发规则；
2. 将现有 judge 调用升级为结构化检索规划器；
3. 生活记录改为按需调用；
4. 移除最近三条事件摘要的固定上下文注入；
5. 保持现有单查询事件回捞作为临时 fallback；
6. 运行离线测试。

### Phase 2：多查询事件检索与聊天回退

1. 新增 pg_trgm 索引迁移；
2. 新增支持用户和日期过滤的事件向量 RPC；
3. 实现 1-5 组查询的向量检索；
4. 实现事件 `content` 多锚点关键词检索；
5. 实现 `chat_messages` 多锚点关键词回退；
6. 复用现有 +/- 5 分钟窗口回捞原文；
7. 运行测试并调整阈值、候选数和查询数。

### Phase 3：Tool-calling

1. 新建 `_tools.ts`；
2. 将同一套记忆和生活记录检索能力暴露为工具；
3. 实现最多 2 轮的 Agent 补查循环；
4. 增加不支持 tools 的模型回退；
5. 记录不同模型的调用成功率、延迟和费用。

### Phase 4：按测试结果优化

1. 判断是否需要为事件增加 `search_terms`；
2. 优化查询规划器提示词；
3. 根据实际数据调整软时间窗口和候选排序；
4. 决定是否扩展更多 Supabase 数据工具；
5. 评估长期画像何时具备进入上下文的质量。

## 十九、验收标准

- [ ] 极北柳莺样本能检索到当时的历史对话原文。
- [ ] “还记得吗”等明确表达即使模型漏判，也会由代码强制触发历史检索。
- [ ] 检索规划器能输出多组与过去表达有关的查询，而非只重复当前正式名称。
- [ ] `time_hint` 只用于日期范围或优先级，不作为向量或关键词检索文本。
- [ ] 精确和相对日期条件在事件向量 top-N 计算前生效。
- [ ] 事件层未命中时能够直接搜索历史聊天并回捞附近原文。
- [ ] 普通闲聊不再固定注入生活记录。
- [ ] 最近三条事件摘要不再固定进入聊天上下文。
- [ ] 最终上下文继续按真实时间统一排序。
- [ ] 现有对话定位方式、消息角色和最后一条 thinking 行为保持不变。
- [ ] 不支持 Tool-calling 的模型仍可使用程序预检索。
- [ ] 检索过程具备可查看的调试信息和阶段耗时。
- [ ] 实现完成后同步更新 AI、API、数据库和数据流说明文档。
