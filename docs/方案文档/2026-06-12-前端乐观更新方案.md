# 前端乐观更新方案

> 状态：方案设计阶段，待用户确认后实施  
> 日期：2026-06-12  
> 说明：本方案聚焦消除记账时的"记录中"等待时间，以及通过 HarmonyOS RelationalStore 实现本地缓存加速。

---

## 一、功能名称

前端乐观更新：记账即时显示 + 本地缓存层。

---

## 二、背景与动机

### 2.1 当前痛点

用户记账时的完整链路：

```
用户输入 "午餐麦当劳35"
  → POST /api/parse-transaction (Vercel)
    → AI 解析 (DeepSeek, 1-3s)  ← 主要瓶颈
      → 写入 Supabase (50-150ms)
        → 返回结果 → 前端刷新列表
```

用户等待 "记录中..." 的时间中，**约 80% 花在 AI 解析上**，数据库写入和网络传输只占很小比例。

### 2.2 为什么不迁移到本地数据库

经过分析，把数据从 Supabase 迁移到 HarmonyOS RelationalStore 对"记录中"延迟的改善微乎其微——AI 解析的 1-3 秒才是瓶颈，与数据库在哪里无关。且全面本地化会失去：

- Web 端（fsync.top）访问能力
- 云端自动备份
- 主动消息和定时任务（依赖服务端）

因此采用**前端优化**方案，在不改变架构的前提下消除感知延迟。

---

## 三、设计目标

- [ ] 记账提交后**立即显示**在列表中，用户感知延迟为 0
- [ ] AI 解析在后台静默完成，结果自动回填
- [ ] 解析失败时有明确的状态标识和重试入口
- [ ] 通过 HarmonyOS RelationalStore 实现本地缓存，加速冷启动
- [ ] 不影响现有数据流和 API

## 五、设计方案

### 5.1 乐观更新流程

```
用户输入 "午餐麦当劳35" → 点击提交
  │
  ▼
前端生成临时 ID: temp_20260612_143052
  │
  ▼
立即插入 optimistic transaction 到本地列表
  {
    id: "temp_20260612_143052",
    type: "记账",
    content: "午餐麦当劳35",
    amount: null,        // 待 AI 解析
    finance_category: null,
    status: "parsing"    // 解析中
  }
  │
  ▼
用户看到卡片立即出现在列表中（带 "解析中..." 小标记）
  │
  ▼
后台发起 API 调用（不阻塞 UI）
  POST /api/parse-transaction { text: "午餐麦当劳35" }
  │
  ├── 成功（~2s 后）
  │     └─→ 替换临时记录为正式记录
  │         {
  │           id: "uuid-from-supabase",
  │           amount: 35,
  │           finance_category: "食",
  │           status: "synced"
  │         }
  │
  └── 失败（网络异常 / AI 解析失败）
        └─→ 标记为 status: "error"
            显示 "解析失败，点击重试"
            用户可手动编辑或重新提交
```

### 5.2 Transaction 状态模型

```typescript
type TransactionStatus = 'parsing' | 'synced' | 'error' | 'local_draft'

interface Transaction {
  id: string                       // UUID 或 temp_xxxxx
  type: string
  content: string
  amount: number | null
  finance_category: string | null
  mood: string | null
  review: string | null
  necessity: boolean | null
  repurchase_index: number | null
  details: string | null
  created_at: string
  status: TransactionStatus       // 新增状态字段
  // 以下字段仅前端使用，不存入 Supabase
  _tempId?: string                // 临时 ID，用于匹配
  _parseError?: string            // 解析错误信息
}
```

### 5.3 状态转换图

```
                提交
                 │
                 ▼
            ┌─────────┐
            │ parsing │  ← 卡片显示灰色虚线边框 + "解析中..."
            └────┬────┘
                 │
        ┌────────┼────────┐
        ▼        ▼        │
   ┌─────────┐ ┌──────┐   │
   │ synced  │ │error │   │ (超时 30s 也视为 error)
   └─────────┘ └──┬───┘   │
                  │       │
         用户点击重试──────┘
```

### 5.4 UI 状态呈现

| 状态 | 视觉表现 |
|------|----------|
| `parsing` | 卡片正常显示，右下角小标记 "⏳ 解析中..."（灰色文字），内容区显示用户原始输入 |
| `synced` | 正常显示，已解析的字段（金额、分类）高亮 |
| `error` | 卡片边框变黄，右下角 "⚠️ 解析失败 点击重试"，内容区保留原始输入 |

### 5.5 与列表操作的兼容

乐观记录在 `parsing` 状态的交互限制：

| 操作 | parsing 状态 | synced 状态 |
|------|-------------|-------------|
| 编辑 | ✅ 允许（编辑原始内容，触发重新解析） | ✅ 允许 |
| 删除 | ✅ 允许（取消后台请求） | ✅ 允许 |
| 查看详情 | ✅ 允许（显示基本信息 + 解析中提示） | ✅ 允许 |
| 导出 | ❌ 跳过（等待 synced 后再包含） | ✅ 允许 |

### 5.6 后台请求管理

使用 `AbortController` 管理进行中的解析请求：

```typescript
const pendingParses = new Map<string, AbortController>()

async function submitTransaction(text: string) {
  const tempId = `temp_${Date.now()}`
  const controller = new AbortController()

  pendingParses.set(tempId, controller)

  // 1. 立即插入乐观记录
  addOptimisticTransaction({ id: tempId, content: text, status: 'parsing' })

  try {
    // 2. 后台解析
    const result = await fetch('/api/parse-transaction', {
      method: 'POST',
      body: JSON.stringify({ text }),
      signal: controller.signal
    })

    // 3. 替换临时记录
    replaceTransaction(tempId, await result.json())

  } catch (err) {
    if (err.name === 'AbortError') {
      // 用户取消了（删除记录时自动 abort）
      removeTransaction(tempId)
    } else {
      // 解析失败
      updateTransactionStatus(tempId, 'error', err.message)
    }
  } finally {
    pendingParses.delete(tempId)
  }
}
```

### 5.7 Phase 2：HarmonyOS RelationalStore 本地缓存

Phase 1 解决了"记录中"延迟后，Phase 2 通过本地缓存进一步优化冷启动速度。

#### 5.7.1 缓存策略

```text
应用启动
  │
  ▼
读取 RelationalStore 本地缓存 → 立即渲染列表（< 100ms）
  │
  ▼
后台同步 Supabase → 更新缓存 + 差异合并
```

缓存内容：
- 最近 200 条 transactions
- 最近 500 条 chat_messages（可选，对话历史通常不需要离线）
- items 表全量（数据量小）
- 用户设置

#### 5.7.2 HarmonyOS 侧实现


#### 5.7.3 前端同步逻辑

```typescript
// src/api/cache.ts
class LocalCache {
  async getRecentTransactions(limit: number): Promise<Transaction[]> {
    if (window.FSyncNative) {
      // HarmonyOS 环境：读本地 RelationalStore
      const rows = await window.FSyncNative.db.query(
        'SELECT data FROM transaction_cache ORDER BY synced_at DESC LIMIT ?',
        [limit]
      )
      return rows.map(r => JSON.parse(r.data))
    } else {
      // 浏览器环境：读 localStorage（降级方案）
      const raw = localStorage.getItem('fsync-cached-transactions')
      return raw ? JSON.parse(raw) : []
    }
  }

  async syncFromSupabase(): Promise<void> {
    const latest = await fetch('/api/transactions?limit=200').then(r => r.json())
    // 更新本地缓存
    if (window.FSyncNative) {
      for (const tx of latest) {
        await window.FSyncNative.db.execute(
          'INSERT OR REPLACE INTO transaction_cache (id, data, synced_at) VALUES (?, ?, ?)',
          [tx.id, JSON.stringify(tx), Date.now()]
        )
      }
    }
    // 降级：localStorage
    localStorage.setItem('fsync-cached-transactions', JSON.stringify(latest))
  }
}
```

## 六、边缘情况

- [x] **快速连续提交**：每个提交独立生成 tempId，并行解析，按创建时间排序
- [x] **解析超时**：30 秒超时，自动标记为 `error`，提示用户手动编辑
- [x] **应用关闭时解析未完成**：重新打开时，`parsing` 状态的记录自动发起重试
- [x] **解析结果与原始输入不一致**：始终以 AI 返回为准；用户不满意可手动编辑
- [x] **网络恢复后的同步**：`error` 状态的记录可批量重试
- [x] **localStorage 容量限制**：仅缓存最近 50 条，超出自动淘汰最早的数据

## 七、与现有功能的交互

| 现有功能 | 影响 |
|----------|------|
| 记账表单 | 提交后立即关闭表单，不等待 AI 返回 |
| 交易列表 | 新增 status 字段渲染，乐观记录与正式记录混合显示 |
| 编辑弹窗 | 对 parsing 状态的记录可编辑原始内容 |
| 报表统计 | parsing 状态的记录不参与统计（amount 为 null） |
| 记账日历 | parsing 状态的记录依然显示（使用 created_at） |
| 离线草稿 | 原有草稿箱功能与乐观更新互补，不冲突 |
