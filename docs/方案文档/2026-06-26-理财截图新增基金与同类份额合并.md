# 理财截图新增基金与同类份额合并

> 状态：已实现
> 日期：2026-06-26

---

## 功能名称

理财截图识别结果支持新增未收录基金，并自动合并同一基金的 A/C/E 类份额。

---

## 背景与动机

当前理财截图识别流程只会把名称匹配到现有 `investments` 记录的基金套入本地草稿。数据库中不存在的基金会标记为“未匹配”，不能继续应用；同一基金的不同份额类别（例如 A 类与 C 类）也可能显示为两个条目。

本次改造需要：

1. 允许用户把未匹配结果新增为持仓基金，名称默认采用 OCR 结果，也可以在确认前手动填写完整名称。
2. 对只差 A/C/E 份额类别的同一基金进行合并，避免识别结果和持仓列表出现重复条目。
3. 保持现有“先套入本地草稿，再点击总保存同步”的使用习惯。

---

## 设计目标

- [x] 未匹配基金可在识别结果弹窗中直接新增。
- [x] 新基金名称默认使用 OCR 结果，并允许用户手动修改全称。
- [x] 同一基金的 A/C/E 类份额自动合并为一个识别结果。
- [x] 合并后的持仓金额和收益率能够代表各份额类别的合计持仓。
- [x] 使用保守、可解释的名称规则，避免把名称相似但实际不同的基金误合并。
- [x] 新基金和现有基金修改统一通过页面总保存按钮写入 Supabase。

## 设计方案

### 数据流

```text
用户选择一张或多张截图
  → OCR 返回基金条目
  → 名称标准化
  → 完全重复条目按现有规则去重
  → 只差 A/C/E 份额类别的条目合并
  → 尝试匹配现有持仓
  → 识别结果弹窗
       ├─ 已匹配：显示目标基金
       └─ 未匹配：默认勾选“新增基金”，名称可编辑
  → 点击“应用识别结果”
  → 已匹配项写入 pendingUpdates
  → 新基金写入 pendingCreates，并以临时 ID 显示在持仓表
  → 点击总“保存 N”
  → POST /api/investment type=batch_update
  → 批量更新现有基金 + 创建新基金
  → 重新读取 Supabase 持仓，替换临时 ID
```

### 名称标准化

继续沿用当前匹配前处理：

- 移除全部空白。
- 移除中文、英文圆括号符号，但保留括号内文字。
- 移除截断省略号。
- 移除常见中英文逗号、句号。

新增“份额类别拆分”：

```typescript
type FundNameParts = {
  normalizedName: string
  familyName: string
  shareClass: 'A' | 'C' | 'E' | null
}
```

只识别名称末尾明确出现的 `A`、`C`、`E` 或 `A类`、`C类`、`E类`。移除该后缀后的名称作为 `familyName`。

示例：

| OCR 名称 | familyName | shareClass |
|----------|------------|------------|
| `某某增强债券A` | `某某增强债券` | `A` |
| `某某增强债券 C类` | `某某增强债券` | `C` |
| `某某增强债券E` | `某某增强债券` | `E` |
| `某某增强债券` | `某某增强债券` | `null` |
| `某某90天持有A` | `某某90天持有` | `A` |

不使用通用编辑距离或“相似度百分比”自动合并，避免误合并以下基金：

- `90天持有` 与 `180天持有`
- `普通指数` 与 `指数增强`
- `联接基金` 与对应 ETF
- 名称主体只有一两个字不同的不同产品

### OCR 条目合并规则

合并分为两类，计算方式不同。

#### 1. 完全重复

适用于同一基金在多张重叠截图中重复出现，判断条件为：

- 已匹配到同一个 `investmentId`；或
- 标准化后的完整名称完全相同。

处理规则保持现状：后识别到的非空持仓金额、收益率覆盖前值，不把金额相加，避免重叠截图导致重复计入。

#### 2. 同类份额合并

仅当以下条件全部满足时自动合并：

- 两个条目的 `familyName` 完全相同，且长度不少于 4 个字符。
- 至少出现两个不同且明确的份额后缀，例如 A 与 C。
- 条目的差异仅为末尾 A/C/E 份额类别。

处理规则：

- `holding_cents`：各份额类别持仓金额相加。
- `profit_rate`：当各条目都有合法持仓金额和收益率时，根据各自持仓成本合并：

```text
单笔成本 = 当前持仓 / (1 + 收益率)
合并收益率 = 合计当前持仓 / 合计成本 - 1
```

- 如果只有一条有有效收益率，则沿用该收益率。
- 如果无法安全计算，则收益率留空，等待用户手动填写。
- 识别结果中标记“已合并 A/C 份额”，并展示合并前的名称。

例如：

```text
某基金A：持仓 1,100 元，收益率 10%
某基金C：持仓 900 元，收益率 -10%

合并持仓：2,000 元
合并成本：1,100 / 1.10 + 900 / 0.90 = 2,000 元
合并收益率：0%
```

### 合并后的现有基金匹配

同类份额合并后再选择目标持仓：

1. 如果合并组内只有一个条目匹配现有基金，合并结果使用该基金 ID。
2. 如果多个条目都匹配到同一个基金 ID，直接使用该 ID。
3. 如果 A 类和 C 类分别匹配到两个不同的现有基金 ID，识别结果仍合并为一行，但显示“选择合并到”下拉框；默认不应用，必须由用户选择目标基金。
4. 如果没有匹配项，则作为待新增基金处理。

该规则避免在数据库已分别维护 A/C 类时，静默覆盖其中一只基金。

### 未匹配基金交互

识别结果弹窗中的未匹配项不再降低透明度并直接跳过，而是显示：

- 状态：`待新增`
- 复选框：`新增到持仓`，默认勾选
- 基金名称输入框：默认填入 OCR 名称，可手动补全或修正
- 当前持仓、收益率：沿用 OCR 结果；识别为空时允许在弹窗中填写
- 提示：`目标持仓暂按当前持仓设置，可稍后在“管理持仓”中调整`

名称留空时不能应用该条目。用户取消勾选后，本次忽略该基金。

### 新基金安全默认值

截图只能稳定提供基金名称、当前持仓和收益率，不能可靠提供策略参数。新增记录采用以下默认值：

| 字段 | 默认值 | 原因 |
|------|--------|------|
| `fund_name` | 用户确认后的名称 | OCR 名称可直接使用，也可补全 |
| `fund_code` | `null` | 截图通常没有代码 |
| `current_value_cents` | OCR 金额；为空时 `0` | 保证数据库非空约束 |
| `current_profit_rate` | OCR 收益率；为空时 `0` | 保证数据库非空约束 |
| `target_amount_cents` | 等于当前持仓 | 为后续配置补仓和止盈参数提供中性初始值 |
| `stop_profit_line` | `null` | 不推测策略 |
| `trading_cycle` | `none` | 未配置前不参与常规周/月调仓 |
| `strategy_tag` | `待配置` | 提醒用户后续完善 |
| `notes` | `由截图识别新增` | 标记来源 |

### 前端本地草稿

新增：

```typescript
type PendingInvestmentCreate = {
  tempId: string
  fundName: string
  currentValueCents: number
  currentProfitRate: number
  targetAmountCents: number
  stopProfitLine: null
  tradingCycle: 'none'
  strategyTag: '待配置'
  notes: string
}
```

`pendingCreates` 使用临时 ID 保存。应用 OCR 后，新基金立即显示在当前持仓表，但在点击总保存前不会写入 Supabase。

总保存数量：

```text
pendingCount = pendingUpdates.size + pendingCreates.size
```

取消或重新加载页面时，未保存的新基金与现有本地草稿一样会丢失。

### API 设计

继续复用现有 Serverless Function：

```http
POST /api/investment
```

扩展 `type=batch_update`：

```json
{
  "type": "batch_update",
  "userId": "uuid",
  "updates": [
    {
      "investmentId": "uuid",
      "currentValueCents": 60000,
      "currentProfitRate": 0.15
    }
  ],
  "creates": [
    {
      "clientId": "ocr:temporary-id",
      "fundName": "某某增强债券",
      "currentValueCents": 200000,
      "currentProfitRate": 0,
      "targetAmountCents": 200000,
      "stopProfitLine": null,
      "tradingCycle": "none",
      "strategyTag": "待配置",
      "notes": "由截图识别新增"
    }
  ]
}
```

`updates`、`creates` 至少一个为非空数组。

响应：

```json
{
  "success": true,
  "updatedCount": 1,
  "createdInvestments": [
    {
      "clientId": "ocr:temporary-id",
      "investment": {
        "id": "uuid",
        "fund_name": "某某增强债券"
      }
    }
  ]
}
```

服务端校验：

- 所有更新记录必须属于 `userId`。
- 新基金名称 trim 后不能为空。
- 金额、收益率必须为有限数字，金额不得小于 0。
- `tradingCycle` 只允许 `weekly`、`monthly`、`none`。
- 先检查请求内新增项是否重名。
- 数据库唯一约束继续防止同一用户出现完全相同的基金名称。
- 遇到重复名称时返回明确错误，不自动覆盖已有持仓。

不新增 API 文件，不占用新的 Vercel Serverless Function。

## 边缘情况

- [x] OCR 名称为空：过滤，不允许新增。
- [x] OCR 金额或收益率为空：输入框允许补充；仍为空时按安全默认值 `0` 创建。
- [x] 合并项中某个收益率小于等于 `-100%`：不计算合并收益率，留空等待用户填写。
- [x] 同一基金跨多张截图重复：覆盖数据，不相加。
- [x] A/C/E 类是截图中的不同持仓：金额相加，收益率按成本合并。
- [x] 两个份额类别分别匹配到不同数据库记录：要求用户选择合并目标。
- [x] 新基金名称与数据库已有名称完全重复：保存失败并提示用户返回修正或取消新增。
- [x] 用户关闭识别结果弹窗：不产生本地草稿或数据库写入。
- [x] 批量保存失败：保留本地草稿，允许用户重试。
- [x] 页面刷新：未保存草稿丢失，与现有理财编辑行为一致。

## 需要用户确认的设计决策

1. A/C/E 类合并后，持仓金额相加，收益率按持仓成本合并，而不是简单取其中一个收益率。
2. 新基金默认 `目标持仓 = 当前持仓`、`调仓周期 = none`、`策略标签 = 待配置`，用户稍后在“管理持仓”中完善。
3. 如果 A 类和 C 类已经分别对应数据库中的两只基金，不静默选择其中一只，而是要求用户选择合并到哪一只。
4. “几乎完全一样”只覆盖完整同名和末尾份额类别差异，不启用宽泛的模糊字符串合并。
